# Advisory Services: coordinated production launch runbook

Status: **prepared, not executed.** Nothing in this document has been run against production. Every step below needs the owner's explicit go-ahead on the day. Prepared 2026-10-28 on branch `feature/advisory-services`.

Companion documents: `advisory-release-readiness.md` (the Step 5 audit), `advisory-production-readiness.md` (older checklist), `advisory-daily-webhook-live-test.md` (how Daily's webhook behaves).

## 0. Decisions this runbook is built on

1. The old Render backend is stopped. Production is AWS Lightsail (backend), Vercel (frontend), Supabase PostgreSQL (database).
2. The production website design does not change. (Verified, section 2.)
3. At most **2 pending consultation requests per founder** (across all advisors and startups). Built and tested.
4. Advisory Services is public as soon as the release completes: one coordinated release, no prolonged dark period.
5. Order is fixed because AWS and Vercel deployments are not atomic: **database, backend configuration, backend code, webhook, then the frontend switch last** (section 5).

## 6. Daily.co webhook procedure

1. Pre-condition: step 3 passed, in particular the probe returned **401**. (404 means `ADVISORY_ENABLED` is off or `DAILY_WEBHOOK_SECRET` is missing on the backend: fix that first. Registering earlier would make Daily's creation-time test ping fail.)
2. In a shell: `DAILY_API_KEY` and `DAILY_WEBHOOK_SECRET` (the same value that is on the backend) set for that process only, then:
   `$env:DAILY_WEBHOOK_CONFIRM = "REGISTER ruwad-backend.vaykv052p845y.ap-southeast-2.cs.amazonlightsail.com"; node backend/scripts/ops/daily-webhook-production.js register`
3. The script refuses unless the secret is well formed, the confirmation matches, the endpoint is ready, and no webhook already points at that URL. It creates one webhook for `participant.joined` and `participant.left` with `retryType: exponential`, then re-reads the account and requires `ACTIVE`.
4. Daily's creation-time test ping must be answered with HTTP 200 within 8 seconds: the endpoint returns `{"status":"test"}`.
5. Facts already proven live (Step 4): signature is HMAC-SHA256 over `timestamp.rawBody` with the base64-decoded secret; `X-Webhook-Timestamp` is in milliseconds; retries keep the event id with a fresh timestamp about 3.6 s later; the 300 s tolerance is safe.
6. Rollback: `$env:DAILY_WEBHOOK_CONFIRM = "DELETE <uuid>"; node backend/scripts/ops/daily-webhook-production.js delete <uuid>`. Without the webhook, consultations still work; attendance is then not recorded automatically and the Needs Review queue covers it.

## 9. Partial deployment failure: what state you can be in, and what to do

Principle: each step leaves the public site working. The feature only becomes visible at step 5, so any failure before it leaves RUWAD looking exactly as it does today.

| Failure | State | Action |
| --- | --- | --- |
| Step 1 migration fails | all four are in one transaction, so nothing applied | `plan` to confirm; fix the cause; nothing public changed. If `plan` says "partly applied", stop and investigate before anything else. |
| Step 2 configuration fails or the deployment is unhealthy | Lightsail keeps serving the previous deployment | read the deployment error; re-run with corrected values; the site is unchanged. |
| Step 3 workflow fails at build or health | Lightsail keeps the previous deployment; the environment already has `ADVISORY_ENABLED=true`, which the old image ignores | fix forward or leave. The Vercel build of the same commit, if it ran, has the flag unset and is identical to today's site. Do not continue. |
| Step 3 succeeds but gate G3 shows an Advisory problem | backend live, no UI, no webhook | leave the frontend switch off. Fix forward, or set `ADVISORY_ENABLED` back off (section 11, level 2). |
| Step 3 succeeds but an **existing** feature regressed | the new image is live | roll the backend back at once (section 11, level 3). The Advisory tables are additive; the old code runs against the new schema. |
| Step 4 webhook registration fails | feature not yet public | read Daily's message (usually the endpoint was not ready or the secret differs); do not open the feature until attendance works, or accept manual attendance (Needs Review) knowingly. |
| Step 5 Vercel build fails or hangs | the previous production deployment keeps serving; the feature is simply not visible | retry the redeploy; the backend side is harmless in the meantime (no advisors, applications need a signed-in user). |
| Step 5 is live but the backend degrades | users see Advisory errors | section 11, level 1 immediately (UI off), then investigate. |
| Smoke test fails | feature public | level 1 (UI off) while diagnosing; data is kept. |
| Daily or Resend outage later | meetings cannot open, or emails fail | bookings stay safe; emails are logged and do not block actions; Needs Review covers attendance; no rollback needed. |

## 11. Rollback (disable Advisory without destroying data)

Fastest and safest first. None of levels 1 to 3 deletes any row.

| Level | Action | Effect |
| --- | --- | --- |
| 1. Hide the feature | Vercel: delete `NEXT_PUBLIC_ADVISORY_ENABLED` and redeploy (or promote the previous deployment: instant) | nav entries gone, all 7 Advisory pages 404; backend still running |
| 2. Switch the API off | `node infra/aws/set-lightsail-env.js --profile ruwad --unset ADVISORY_ENABLED --unset ADVISORY_SCHEDULER_ENABLED` (and optionally `--unset ADVISORY_EMAIL_MODE`) | every Advisory route is a 404; no scheduler, no emails; **all data kept** |
| 3. Previous backend code | `node backend/scripts/ops/lightsail-rollback.js plan 10` (read-only: shows which variable names would be removed or added), then `$env:LIGHTSAIL_ROLLBACK_CONFIRM="ROLLBACK-LIGHTSAIL ruwad-backend TO-VERSION-10"; node backend/scripts/ops/lightsail-rollback.js apply 10`. It creates a new deployment from version 10's exact configuration (image `api.8`, the original environment) and waits for ACTIVE and health. To keep the Advisory environment but run the old code, roll back to version 11 instead (the environment-only deployment). The migrations stay (additive; old code ignores them). | existing behaviour as before the release |
| 4. Remove the webhook | `daily-webhook-production.js delete <uuid>` | Daily stops calling the backend |
| 5. Schema (last resort, only if nobody has used the feature) | four times, from a controlled shell with the direct connection string: `$env:ADVISORY_MIGRATIONS="true"; $env:DATABASE_SSL="true"; $env:DATABASE_URL="<direct connection string>"; npm run migration:revert --workspace backend` (each run reverts the newest applied migration; check with `advisory-migrate.js plan` between runs). **Always set `DATABASE_URL` explicitly: if it is missing the CLI falls back to `backend/.env`.** | drops the advisory tables **and their data**; after real use, prefer levels 1 to 4 |

**No backup exists (accepted risk).** If something damaged existing data there would be no copy to restore from other than whatever the Supabase plan holds, which has not been verified. The release is built so that this cannot happen through the migrations (additive only, one transaction, rehearsed on a production-equivalent copy, proven unchanged by P2b), but a mistake made by hand in the database would not be recoverable. Nothing in the rollback levels above depends on a backup.

## 12. Downtime and residual risk
